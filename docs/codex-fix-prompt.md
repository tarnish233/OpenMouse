## 硬性要求

1. **每修一条缺陷，补一条断言。** 报告里「应补断言」那栏是要求，不是建议。缺陷复发是
   这个项目反复踩过的坑，断言是唯一的防线。
2. **不要为了让测试通过而改断言本身或注释掉 `group(...)`。** 断言失败意味着代码还没修好。
3. **不要改动与 Mos 对齐的手感常数**：`33.6`、`2.70`、`0.085`、`0.23`。自检里专门有一组钉着它们。
4. **不要把 `.swiftLanguageMode(.v5)` 改成 v6。** 事件 tap 是 C 函数指针回调 + `Unmanaged`，
   Swift 6 的严格隔离只会让这层充满仪式性样板。这是刻意的选择。
5. **不要用全局键盘 tap 探测键码**——那会捕获用户的真实输入。需要验证按键有效性时用
   「注入 + 读系统日志」（`/usr/bin/log show --predicate 'subsystem == "com.apple.dock"'`），
   并注意注入进程必须存活 ~400ms，否则 WindowServer 不处理队列（会造成假阴性）。
   用 `/usr/bin/log` 的全路径——`log` 在这台机器上被 shell 函数遮蔽了。
6. **不要 commit 或 push。** 改完让我 review。
7. 遇到报告里标「待确认」的条目：先自己确认触发条件是否真实存在，再决定修法。判断不了就
   在报告里说明并跳过，不要猜。

## 关于「修复要建立的性质」

报告刻意只给性质，不给补丁。实现方式你定，但那条性质必须真的成立。特别是：

- 报告里写明了几个**看起来能修但修不了**的做法（例如 F1「单纯把 `running = false` 挪到
  `stopTicker()` 之后没用」），不要往那些方向走。
- 多条缺陷的共同成因是「约束靠每个调用点自己遵守，而不是收在一个必经的收口处」
  （见报告 §4.3）。修的时候顺手想一下能不能让下一次漂移编译不过或被断言抓住。

## 关于 §4.2 那两条断言

`hasFallbackForEveryCharacter` 和 `noTwoActionsSendTheSameKeys` 目前是**同义反复**的
（验证的是「这张表等于它自己」）。按报告改正它们之后**会立刻失败**——这是正确的，说明它们
终于开始检查真实的东西了。不要靠回退这两条断言来让测试变绿，要修它们指出的真实缺口。
